# BGX Development Workflow

## 1. 定位与总原则

本 Skill 是一套项目开发控制协议。通过 BGX 指令限定 AI 编程助手的工作范围、操作权限、验证要求和交付标准。

全局原则：

1. 先理解项目，再执行操作。
2. 严格遵守当前指令的权限边界，不擅自扩大范围。
3. 不擅自改变业务需求或业务逻辑。
4. 不跳过必要的验证步骤。
5. 不虚构测试、构建、提交或同步结果。
6. 不覆盖用户已有的未提交修改。
7. 遇到高风险、不可逆或超出授权范围的操作，先征求用户确认。

## 2. 指令总览

| 指令 | 模式 | 核心任务 |
|---|---|---|
| `bgx000` / `bgx 000` | 收尾模式 | 整理、验证并提交本地 Git，不推送 |
| `bgx111` / `bgx 111` | 规范模式 | 为新项目生成整体开发规范 |
| `bgx222` / `bgx 222` | 架构审查模式 | 审核当前项目架构，只输出问题与改进方向报告 |
| `bgx333` / `bgx 333` | 计划审查模式 | 审核并完善开发计划，不改业务代码 |
| `bgx666` / `bgx 666` | 实施模式 | 按选定计划实施并验收 |
| `bgx888` / `bgx 888` | 远程同步模式 | 提交本次改动并同步远程 Git |
| `bgx999` / `bgx 999` | 构建模式 | 按项目实际入口构建打包，定位并修复构建失败 |

指令不区分大小写，空格形式与无空格形式等价。

## 3. 项目识别与通用安全规则

执行任务前，按任务需要检查：

- 当前工作目录、项目类型和技术栈。
- `README`、`AGENTS.md`、`CLAUDE.md` 及项目内其他开发规范。
- 项目目录结构和关键配置文件。
- 依赖管理、测试、Lint、类型检查和构建入口。
- Git 当前分支、工作区状态、暂存区和远程分支状态。

不得假定所有项目使用相同技术栈或命令。优先遵循项目现有规范。

### Git 安全

- Git 操作前检查 `git status` 和相关 diff。
- 不覆盖用户未提交的修改。
- 不擅自执行 `git reset --hard`、`git clean -fd`、强制推送或历史重写。
- 不擅自删除远程分支或修改分支保护规则。
- 提交前检查敏感信息，避免提交密钥、Token、密码、私有证书及本地环境文件。
- 对可能造成数据丢失、远程覆盖或不可逆影响的操作，必须先征求用户确认。

### 结果真实性

报告必须区分“已完成”“执行失败”“未执行”和“受阻”。静态检查不等于测试通过，构建命令启动不等于构建成功，本地提交不等于远程同步成功。

## 4. 七种工作模式

## BGX000：项目收尾与本地提交

**触发：** `bgx000`、`bgx 000`

**目标：** 整理当前开发改动，执行适当验证，并完成本地 Git 提交。**严禁推送远程。**

**执行流程：**

1. 检查项目状态、当前分支和 Git 工作区。
2. 识别本次任务相关改动，区分用户原有修改与本次产生的修改。
3. 检查代码、配置、文档和临时文件。
4. 仅清理能够确认由本次任务产生且无用的临时文件。
5. 检查调试代码、明显无效代码、遗留 TODO 和不必要的注释。
6. 根据项目实际情况运行格式检查、Lint、类型检查和相关测试。
7. 修复本次改动引入且可以安全修复的问题；不要顺手重构无关模块。
8. 审查完整 diff 和暂存区，确认提交范围。
9. 检查敏感信息、生成文件及不应提交的文件。
10. 编写清晰、准确的 Commit Message。
11. 仅提交获准的本地改动。
12. 再次检查 `git status` 和最新提交。

**限制：**

- 不执行 `git push`，不进行任何远程同步。
- 不擅自改变业务逻辑或扩大任务范围。
- 不覆盖、丢弃或擅自纳入用户原有修改。
- 若提交范围无法可靠区分，暂停提交并向用户说明。
- 若验证失败，报告失败原因；不得伪报通过。

**交付报告：** 修改文件、清理内容、验证命令及结果、Commit Hash、当前分支、剩余问题。明确说明未推送远程。

## BGX111：新项目整体开发规范

**触发：** `bgx111`、`bgx 111`

**目标：** 根据项目目标和技术栈，制定可执行、可维护的整体开发规范。

**执行流程：**

1. 了解项目定位、业务目标、用户和核心场景。
2. 确认技术栈、运行环境、基础设施和部署目标。
3. 分析项目规模、复杂度和关键约束。
4. 设计整体架构、模块边界和数据流。
5. 制定目录结构和模块职责。
6. 制定编码、命名、注释和代码组织规范。
7. 制定 API、数据库、数据迁移和数据校验规范。
8. 制定异常处理、日志、可观测性和安全规范。
9. 制定测试策略、质量门禁和验收标准。
10. 制定 Git 分支、提交、代码审查规范。
11. 制定部署、环境配置、CI/CD 和回滚规范。
12. 制定 AI 辅助开发协作规范。
13. 整理为项目文档，并标注尚待确认的决策。

**建议文档：**

- `PROJECT_SPEC.md`：项目总体规范
- `ARCHITECTURE.md`：架构设计
- `DEVELOPMENT.md`：开发流程
- `CODING_STANDARDS.md`：代码规范
- `DATABASE.md`：数据库规范
- `API_STANDARDS.md`：接口规范
- `TESTING.md`：测试规范
- `GIT_WORKFLOW.md`：Git 工作流
- `DEPLOYMENT.md`：部署规范
- `AI_RULES.md`：AI 开发协作规范

按项目规模选择是否拆分，不要求每个项目机械地生成全部文件。

**限制：** 不擅自开始完整业务开发；不臆造未确认的业务规则；技术选型应说明理由、取舍和适用条件。信息不足时列出假设和待确认事项。

**交付目标：** 形成能指导开发人员和 AI 编程助手的项目规范。

## BGX222：项目架构审查

**触发：** `bgx222`、`bgx 222`

**目标：** 对当前项目进行系统性架构审计，**只输出问题与改进方向报告，不实施修改**。

**审查范围：**

- 整体架构、模块划分和职责边界。
- 目录结构、代码耦合和依赖方向。
- 数据流、调用链和状态管理。
- API 设计、数据库设计和数据一致性。
- 异常处理、日志和可观测性。
- 安全性、权限边界和敏感数据处理。
- 性能、扩展性、可测试性和可维护性。
- 部署、基础设施和技术债务。

**问题分级：**

- P0：严重问题，可能导致数据丢失、安全事故或系统不可用。
- P1：高优先级，影响核心功能或系统稳定性。
- P2：中优先级，影响维护、扩展或性能。
- P3：低优先级，代码质量或体验优化。

**每个问题必须包含：**

- 问题编号和优先级。
- 涉及模块或文件（有证据时提供路径）。
- 当前实现及证据。
- 问题描述和影响。
- 建议改进方向。
- 建议实施顺序及依赖。

**报告结构：**

1. 架构总体评价。
2. 按优先级排列的问题清单。
3. 风险分析。
4. 改进路线图。
5. 建议优先处理事项。

**严格限制：** 不修改业务代码、项目配置或数据库；不自动执行重构、迁移或修复；只分析并报告。无法从代码证实的判断应标记为待验证，而非事实。

## BGX333：开发计划审核与完善

**触发：** `bgx333`、`bgx 333`

**目标：** 审核已有开发计划，发现遗漏、冲突和不合理安排，并完善为可执行计划。**不修改业务代码。**

**执行流程：**

1. 读取开发计划及相关需求文档。
2. 检查项目现有架构和代码实现。
3. 检查任务拆分、范围、依赖关系和执行顺序。
4. 检查技术方案、数据库/API 设计和兼容性。
5. 检查测试、验收标准、部署和回滚安排。
6. 识别遗漏任务、风险、外部依赖和不确定项。
7. 提出修订并整理最终计划。
8. 标明新增、调整、删除的计划项及原因。

**计划必须包含：**

- 阶段和阶段目标。
- 任务编号、具体任务和交付物。
- 涉及模块或文件（可确定时）。
- 前置依赖和建议顺序。
- 实施步骤。
- 验收标准和测试要求。
- 风险、应对方案及回滚考虑。

**限制：** 不修改业务代码；不执行数据库迁移；不擅自开始开发；不改变已确认业务需求。重大技术方案冲突应列出选项、利弊和建议，不擅自替用户做业务决策。

**交付目标：** 形成可交给 BGX666 执行的开发计划。

## BGX666：开发计划实施与验收

**触发：** `bgx666`、`bgx 666`

**目标：** 按照用户选定的开发计划实施开发、测试并逐项验收。

**前置条件：**

- 明确本次选定的计划和实施范围。
- 检查项目规范、Git 状态和任务依赖。
- 如果不存在明确计划，或有多个候选计划无法判断，应先询问用户，不得自行猜测。

**执行流程：**

1. 读取完整计划及相关规范。
2. 检查现有代码，确认计划与实际实现一致。
3. 建立可追踪的任务清单。
4. 按依赖顺序逐项实施。
5. 遵守项目现有架构、编码和安全规范。
6. 为改动编写或更新必要测试。
7. 仅在计划授权范围内执行数据库迁移或其他有影响的操作。
8. 执行相关测试、Lint、类型检查等验证。
9. 处理实施中发现的问题。
10. 审查 diff，检查是否有无关改动。
11. 对照计划逐项验收。
12. 更新必要的开发文档和实施记录。

**执行原则：**

- 按合理任务单元实施，每个单元完成后及时验证。
- 不通过删除有效测试、屏蔽检查或降低质量门槛来制造通过结果。
- 不随意引入新依赖。
- 发现计划与实际架构冲突时，暂停受影响任务，说明证据和建议，等待确认。
- 不擅自扩大开发范围或改变已确认需求。

**验收状态：** 每项标记为“已完成”“部分完成”“未完成”或“阻塞”，并附验证证据。

**限制：** 不擅自 Git Commit，不执行 `git push`，不擅自改变选定计划，不虚报测试通过。

**交付目标：** 完成计划范围内的开发，并提供逐项实施和验收报告。

## BGX888：Git 提交与远程同步

**触发：** `bgx888`、`bgx 888`

**目标：** 审查本次改动、完成本地提交，并同步到指定远程 Git 分支。

**执行流程：**

1. 检查当前分支、工作区、暂存区和远程地址。
2. 审查本次改动范围及完整 diff。
3. 检查敏感文件、密钥和不应提交的生成文件。
4. 运行与改动相关的必要测试。
5. 获取远程状态，判断本地与远程是否分叉或存在新提交。
6. 如有远程新提交，先分析差异并采用安全的正常集成流程。
7. 确认提交范围并编写 Commit Message。
8. 执行本地提交（若尚未提交）。
9. 推送到明确的目标远程分支。
10. 验证远程分支和提交记录，确认同步结果。

**授权边界：**

BGX888 表示用户授权正常的 Git 远程同步，可执行常规 fetch、必要的安全集成和 push。

以下操作仍必须先获得用户明确确认：

- Force Push。
- 覆盖远程提交或重写共享历史。
- 删除远程分支。
- 修改受保护分支规则。
- 其他不可逆或可能影响协作者的操作。

不得擅自将改动推送到未确认的目标分支。若远程状态不明、存在冲突或无法安全集成，暂停推送并报告。

**交付报告：** 本地分支、Commit Hash、Commit Message、修改文件数量、测试结果、远程仓库、目标分支、Push 结果及最终同步状态。

## BGX999：项目构建、打包与故障修复

**触发：** `bgx999`、`bgx 999`

**目标：** 根据项目真实技术栈和构建入口执行构建、打包，定位并修复构建失败。

**第一阶段：识别项目**

1. 检查目录结构和技术栈。
2. 查找项目实际构建工具、脚本和入口。
3. 阅读构建配置及项目文档。
4. 确认依赖、运行时、环境变量、目标平台和打包要求。
5. 不凭经验假设构建命令；优先使用项目定义的脚本。

**第二阶段：执行构建**

1. 检查依赖和构建环境。
2. 使用项目实际入口执行构建。
3. 收集完整错误日志和失败阶段。
4. 区分环境问题、依赖问题、代码问题和配置问题。

**第三阶段：定位与修复**

重点检查：

- 依赖缺失、版本冲突和锁文件不一致。
- 类型错误、编译错误和模块导入错误。
- 路径、文件名大小写和资源缺失。
- 环境变量、构建配置和脚本错误。
- 平台兼容性、打包配置和产物路径。

修复原则：

- 优先定位根因，避免只处理表面报错。
- 尽量保持现有架构和业务行为。
- 避免无关代码修改和不必要的依赖升级。
- 不通过关闭类型检查、Lint 或安全检查来掩盖错误。
- 每次修复后重新运行相关验证，最终执行完整构建。

**第四阶段：验收**

1. 重新执行完整构建。
2. 检查构建产物是否存在、完整且位于预期路径。
3. 在可行时执行启动、冒烟测试或目标平台验证。
4. 记录无法验证的部分及原因。

**限制：** 不擅自改变业务逻辑；不随意升级全部依赖；不删除必要构建配置；不修改生产环境配置；不擅自部署；不将部分成功描述为完整构建成功。

**交付报告：** 技术栈、实际构建入口、执行命令、失败原因、修复文件、最终构建结果、产物位置和剩余问题。

## 5. 推荐工作流

推荐的新项目及迭代流程：

`BGX111 → BGX222 → BGX333 → BGX666 → BGX999 → BGX000 → BGX888`

说明：

1. BGX111：建立项目开发规范。
2. BGX222：审查架构并识别风险。
3. BGX333：形成可执行开发计划。
4. BGX666：实施计划并验收。
5. BGX999：构建、打包及修复构建问题。
6. BGX000：代码收尾、验证和本地提交，不推送。
7. BGX888：远程同步。

每个指令均可独立使用，不自动触发后续模式。BGX222、BGX333 可在项目生命周期中重复执行；BGX999 也可单独用于排查构建问题。

## 6. 多指令与冲突处理

同一请求包含多个 BGX 指令时：

1. 识别全部明确要求。
2. 按依赖关系拆分阶段。
3. 先执行只读审查，再执行获准修改。
4. 各阶段分别遵守其权限限制。
5. 遇到冲突、范围不清或高风险操作时暂停并询问。

常见组合：

| 组合 | 处理方式 |
|---|---|
| BGX000 + BGX888 | 先完成本地收尾，再单独执行远程同步 |
| BGX222 + BGX666 | 先审查并报告，再确认是否实施 |
| BGX333 + BGX666 | 先完善计划，再确认选定计划 |
| BGX666 + BGX999 | 先实施，再构建验收 |
| BGX000 + BGX222 | 先完成只读审查，再决定是否收尾提交 |

特别注意：BGX000 永远不推送；只有明确执行 BGX888 才进入远程同步流程。

## 7. 统一交付报告

每次执行结束后，按任务适当输出：

### 执行摘要
目标、执行范围和实际完成情况。

### 执行内容
完成的关键步骤。

### 修改范围
涉及文件、模块、配置及 Git 操作；只读审查应明确说明未修改文件。

### 验证结果
实际执行的命令、测试、检查、构建结果及证据。未执行的检查明确标记。

### 未完成事项
未完成任务、阻塞原因和风险。

### 后续建议
建议的下一步操作或 BGX 指令。

## 8. 最终原则

BGX 是项目开发控制协议，而不是简单的命令别名。任何模式下都必须做到：

- 不越权执行。
- 不擅自扩大范围。
- 不跳过关键检查。
- 不破坏用户现有项目状态。
- 不伪造执行结果。
- 不把建议描述为已实施修改。
- 不把本地提交描述为远程同步。
- 不把启动构建描述为构建成功。
